# Agent 内部文件操作

更新时间：2026-09-10。

## 当前能力

Agent 的内部文件工具直接使用现有资料库接口，不把逻辑路径当作本机路径。普通文本写入使用 `file.write`；删除使用 `file.delete`。本轮新增的是删除工具接入，后端 DELETE 接口及数据库结构不变。

`file.delete` 接受明确的 `nodeId`，仅处理当前 Run 资料库。模型先通过 `file.stat`、`file.resolve` 或目录查询取得本轮已知节点。无法确认身份时拒绝猜测 ID；根目录禁止删除。普通文件直接移入回收站，文件夹必须明确 `recursive=true` 才会连同子树移入回收站。本工具不提供永久删除、清空回收站或本机文件删除。

此操作只修改现有后端节点删除状态，不下载文件，也不删除 MinIO 对象，因此不要求文件所在存储当前可达。回收站恢复继续使用已有系统入口。

## 权限与执行

- 使用既有 main Tool Registry、Run 冻结权限、renderer broker 与提交回执。移入回收站属于可恢复写操作；`full-access` 直接放行，`ask/auto` 使用标准工具确认。不会再弹出文件树自己的删除确认框。
- Renderer 收到 main 绑定的节点名称、类型、父目录、路径及修改时间。开始操作与收集后代后再次查询当前节点，拒绝跨库、移动、重命名、修改或类型变化。每次异步准备后检查 owner，提交前检查取消状态。
- 后端沿用现有权限和事务。客户端重验不等价于原子条件删除：元数据重验与 DELETE 之间仍有短暂并发窗口，未来若需要严格版本条件删除，应扩展后端契约，而非声称已有 CAS。
- 复用 `softDeleteNodeSubtree`：收集后代、执行提交前检查、请求后端、记录提交事实、清理草稿和 Viewer 恢复快照。后端成功即提交回执，不因随后取消、刷新失败或本地清理失败而反转成功。
- HTTP 明确拒绝返回 `uncommitted`；请求发出后连接中断等无法确定的失败返回 `commit_unknown`，提示核对原目录及回收站，禁止盲目重试。

## 界面同步

删除事件带 account/backend/library 范围，由 FileViewerContext 通过现有 `closeTabByNodeId` 关闭预览并释放音视频资源，不新增 tab 状态 owner。发布后的目录刷新机制同时识别 `deleteCommitState=committed`，刷新父目录并标脏树快照；失败和未知结果不冒充成功。成功删除后清除 Run 旧节点感知，后续操作重新查询，避免继续使用已删除节点。

收集子树失败时沿用已有删除服务的尽力清理语义，明确报告本地清理不完整。结果不回传整个子树 ID 清单，避免大目录删除回执超出工具输出预算。

## 实测问题与能力缺口

- 回收站恢复后当前目录树未立即出现文件，切回 Agent 后出现。两个回收站页面的 handleRestore 目前只 markRepositoryTreeSnapshotDirty，没有主动刷新父目录；需纳入所有内部写操作的统一同步，而非把数据恢复成功当作界面同步成功。
- 递归删除任务中模型报告一次计划工具名称校验失败，然后直接调用业务工具成功。失败计划未出现在本轮业务 ToolRun 中；具体请求名称尚未取得，不把模型转述直接当作已定位的校验器缺陷。
- 删除后 Composer 的当前上下文仍曾显示已删除的 check，虽然 main 会清理本轮节点感知且后续执行重验。需要同步清理目录树选中节点和上下文展示。
- 当前 Agent 尚未开放重命名、移动、复制、回收站浏览/恢复及标签管理，不能宣称完整整理流程已验收。已核对后端有 rename、move/batch、recycle、restore 接口及对应 CLI；复制未见独立节点路由，需先明确系统能力和语义。
- directory.create 仍只接受当前目录内的名称，跨目录建目录不具备与其他文件工具一致的 path/nodeId 参数。
