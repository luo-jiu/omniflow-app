# 文件搜索能力与界面形式调研

更新时间：2026-10-02

状态：文件搜索入口和结果界面尚未实施，形式待定；资料库标签及标签名称搜索已落地，见[标签管理](../tag-management.md)和[资料库标签与分页检索](../../../omniflow-go/docs/architecture/library-tags.md)。本文保留文件搜索的候选形式，不指定最终布局。

适用范围：资料库文件工作区的资源搜索，不包含 Agent 会话记录、长期记忆或网页搜索。标签语义另见[资源标签与 Agent 辅助打标](resource-tagging-notes.md)。

## 1. 用户意图与范围

用户希望在文件页面找到搜索入口，主要搜索文件，未来能组合标签筛选。目前尚未决定搜索框以什么形式出现，以及结果如何展示。

本轮目的是查清已有能力、避免重复建设，并保留选择界面的空间。建议先覆盖确定性的文件名、目录范围与标签筛选，再根据实际需求补充正文或语义检索，符合[项目长期方针](../../../PROJECT_PRINCIPLES.md)。

需要分开讨论两个问题：

1. 从哪里发起搜索：常驻输入框、工具栏按钮、快捷键或空白页入口。
2. 在哪里看结果：临时面板、主区域结果页、列表与预览组合等。

两者可以组合，不必“搜索框在哪里，结果就只能在哪里”。

## 2. 当前页面与能力事实

### 2.1 页面不是已有搜索的可用入口

用户截图中的空白内容区属于文件预览区的空状态。仓库中虽然存在旧的 `SearchWorkspace` 组件，但不能据此推断截图正在使用它，也不能视作当前文件搜索已经接通。

工作区状态名 `search-home` 当前承载的是 Agent 模式。未来加入文件搜索时，不应仅凭这个名字复用它而改变 Agent 工作区语义。

### 2.2 后端已有统一元数据查询

`POST /api/v1/nodes/metadata/query` 是优先可复用的基础：

| 参数/能力 | 当前支持 |
| --- | --- |
| 查询模式 | `root`、`children`、`search`、`node` |
| 查询范围 | `libraryId`，以及 `ancestorId` 指定的子树范围 |
| 文件名 | `keyword` 对数据库中存储的 `name` 做不区分大小写的字面子串匹配；另有 `names` 条件 |
| 节点类型 | `nodeType` 区分 `dir` 与 `file` |
| 标签 | `tagIds`，配合 `tagMatchMode: ANY / ALL` |
| 分页 | 游标分页，默认 50 条、最多 100 条；按节点 ID 升序，不是相关性排序 |
| 结果 | 节点身份、名称/扩展名、路径及 `builtInType / archiveMode`；没有完整标签详情或封面投影 |

关键限制：

- 返回路径不代表支持按完整路径关键字搜索；当前关键字条件针对 `name`。
- `name` 与扩展名分开保存，不能保证输入 `.mp3` 等同于文件类型筛选，也不能直接承诺完整文件名搜索。
- 当前不是拼音、错别字容错、语义或正文搜索；`%`、`_` 等按字面查询，不是用户可用通配符。
- 没有扩展名、日期、内置类型、目标种类的通用筛选参数，也没有相关性/时间排序参数或总数。
- 标签查询基于直接关系；给父作品打标签，不会自动让成员文件命中。
- 元数据查询不依赖 MinIO 正文读取。服务端元数据可达而对象存储不可达时，仍可能搜到文件，但不能因此保证能打开正文。

旧 `/nodes/search` 也有名称与标签查询，但缺少同等的游标分页能力，不建议以它另建一套搜索基础。

### 2.3 Agent 搜索的效果与复用边界

| 能力 | 适合什么 | 不适合直接承诺什么 |
| --- | --- | --- |
| Agent 元数据发现 | 查找已知名称、限定目录、组合直接标签 | 语义理解式相关性排序、完整路径匹配 |
| `file.search` | 在候选查询结果上进一步做 glob/文件类型匹配 | 服务端全量 glob 索引、稳定的“每页都有结果” |
| `file.grep` | 在预算内扫描可读 UTF-8 文本的字面内容 | 全库全文索引、PDF/OCR/音视频内容通搜 |
| 会话/记忆搜索 | Agent 自己的会话与记忆数据 | 资料库文件检索 |

`file.search` 有客户端候选页过滤，因此可能出现“本页没有匹配项，但仍有后续页”。不能把它的一次空结果直接显示成整个资料库无匹配。

`file.grep` 没有标签筛选参数；标签加正文检索目前需要先发现范围、再扫描文本。结果也受扫描范围和预算限制，不能当作完整全文检索。

本轮基于代码核查，未做真实大资料库的查全率、延迟或模型调用效果测试。因此结论是“已有确定性检索基础”，不是“搜索效果已经经过实测”。

## 3. 标签筛选需要先明确的语义

例：输入名称关键字，再选择“日语”“助眠”两个标签。已有接口可以表达名称条件与标签条件组合，标签之间可以选择任一满足或全部满足。

标签选择的基础组件已可复用：`LibraryTagPicker` 使用当前库词表，名称搜索和分类过滤在服务端完成，按游标翻页，按明确 ID 回显已选项，不先下载全词表。新标签不再按漫画、ASMR 等资源类型拆分或限制绑定对象；ASMR 的手动编辑也已使用节点增量接口。这些能力并不等于文件搜索页面已经接通。

标签名称搜索与按标签找资源是两条查询链路：前者查库词表，后者查节点直接关系。已有词表索引与关系索引，仍需针对短关键词、热门标签、多标签交集及大目录验证执行计划和延迟；不能仅凭每页限制 50 条保证查询成本。

尚待设计的部分包括：

- 如何将已有标签选择器接入文件搜索，以及条件的整体回显、移除与清空方式。
- 所有标签都按 ANY/ALL，还是“同维度任选、不同维度同时满足”；后者需要更丰富的查询表达式，不能直接等同于现有全局 ANY/ALL。
- 命中作品标签时显示作品，还是另外提供查看其中成员的入口；不应隐式展开全部子文件。
- 是否支持排除标签、无标签资源、别名、保存搜索；这些不属于现有接口的完整能力。

不要先把类型、格式、时长全部做成标签选择项。确定性元数据适合独立筛选，资源标签表达用户整理语义，二者在请求中组合。

## 4. 搜索入口候选

| 形式 | 优点 | 代价与适用条件 |
| --- | --- | --- |
| 文件工具栏紧凑输入框 | 常驻、容易发现，已打开文件时也能用 | 占横向空间，需处理窄窗口与目录树挤压；具体位置待定 |
| 文件工具栏搜索图标，点击展开输入 | 保留工作区空间，符合当前简约图标习惯 | 多一步操作，需明确展开后焦点和关闭行为 |
| 快捷键呼出的轻量搜索面板 | 快速找文件、键盘打开效率高 | 不宜作为唯一入口；标签组合及长结果比较空间不足 |
| 文件空状态内的搜索入口 | 刚进入文件页面时自然可见 | 文件打开后会消失，必须还有持续可达的入口 |

推荐用于下一轮比较的两种组合是“工具栏输入/展开输入 + 主区域结果”和“轻量快捷搜索 + 可进入完整结果”。这是候选原型范围，不代表已经决定同时实现两套入口。

## 5. 搜索结果如何展示

### 5.1 结果占用什么空间

| 形式 | 适用情况 | 主要问题 |
| --- | --- | --- |
| 输入附近的临时结果面板 | 少量候选、快速打开文件 | 长列表、标签组合、连续比较困难；关闭与返回策略需明确 |
| 主内容区结果视图/结果标签页 | 多结果、反复筛选、跨目录比较 | 打开文件后如何返回搜索现场；是否占用标签页待定 |
| 侧边结果抽屉 | 一边保留文件一边找下一个 | 当前已有目录树，会继续压缩预览空间，窄窗口尤其明显 |
| 主区域列表与预览分栏 | 文档或图片逐项比较 | 需要足够宽度；应接入现有预览状态，不能另造独立播放器/预览器 |

暂不建议直接添加常驻的大搜索区或多层卡片。先用代表性任务验证空间是否必要，避免为了搜索把日常文件阅读区长期挤窄。

### 5.2 每条结果长什么样

| 形式 | 适合资源 | 数据与交互要求 |
| --- | --- | --- |
| 紧凑文件列表 | 文件、目录、作品混合结果 | 完整文件名含后缀、类型图标、父级路径；按需要补标签/类型信息 |
| 元数据表格 | 同类大量文件的筛选与比较 | 可用的大小、时间、格式等字段；排序需有后端契约，不能只排序已加载页却表现成全库排序 |
| 封面网格 | 音乐、漫画、视频、ASMR 等作品 | 需要稳定的作品身份、封面与类型投影，不适合强行套到所有普通文件 |

建议先比较紧凑列表，因为它适配混合文件；封面网格可作为作品场景的候选，不要求初版同时具备全部视图。

名称必须显示扩展名，同名资源用路径区分。内置类型与归档模式可消费已有投影；标签详情和摘要只有在可靠获取时才显示，不应为了画完整样式而默认通用查询已提供。

“打开”和“在目录树定位”是两个不同操作。结果项的默认点击行为可沿用已有文件习惯，定位可提供独立入口；最终交互需与工作区统一，不能点击一次就意外改变多个区域。

## 6. 复用架构与状态边界

UI 搜索和 Agent 搜索可以共用查询契约及后端，不必共用 Tool 的结果格式、模型循环或页面组件。用户手动输入关键字不需要先调用 LLM。

建议分层：

- 后端负责账号/资料库授权、节点与标签关系过滤、游标和后续索引能力。
- 通用查询 client 与类型负责请求和基础响应；节点元数据 client 目前在 Agent feature 内，文件搜索实施时按必要范围提取，避免文件页面依赖 Agent 执行器。标签 client 已位于 `features/tag-management/services/tag.api.ts`，直接复用库范围查询。
- UI 搜索负责输入、筛选、加载、结果与返回现场；Agent 适配层继续负责有界 Tool 输出、候选扫描与 Run 权限。
- 文件打开复用既有节点身份和 `FileViewerContext`；目录、内置类型及归档依既有分发规则处理。
- 目录定位复用祖先展开与选中滚动链路；归档隐藏成员、目录树收起、节点已删除等情况需要单独处理，不能保证每条结果立即能在树上看见。

若新增搜索模式，页面负责工作区编排，搜索 feature 负责查询状态，不复制 Agent 会话状态或文件预览状态。结果页、弹出面板和搜索标签页的最终 owner 要在选定交互形式后明确。

查询状态至少包含账号/服务端/资料库、目录范围、关键字、标签和分页条件。新条件到来时重置游标并丢弃旧响应；切换资料库不能短暂显示上一个库的结果。

文件打开后返回搜索，应能保留条件、已加载结果与滚动位置。改名、移动、删除、标签修改后需要使结果失效或更新；不能一直显示过期路径。是否跨重启保留搜索属于待定偏好，不是必须持久化的新业务数据。

## 7. 能力扩展与展示状态

初期可复用“名称子串 + 目录范围 + 文件/目录 + 直接标签 + 游标分页”。如果完整文件名/扩展名筛选是基本体验，需先补明确查询契约，不能藏在不完整的客户端过滤里。

后续按使用证据增加：类型与日期筛选、可解释的排序、正文索引、OCR/字幕文本、语义检索。索引是可重建派生数据，要跟随原节点权限、删除与内容版本失效；不要让它成为另一份标签事实源。

界面必须区分以下情况：

- 没输入条件、正在查询、正在加载后续页、已查完且无匹配。
- 只加载了部分结果；没有总数时只能说“已加载”，不能把 50 条称作总共 50 条。
- 网络/权限错误；不能表现为无结果。
- 元数据可见但正文不可达；搜索成功与打开成功分开处理。
- 若未来显示正文命中，区分索引尚未完成、被跳过文件与已覆盖范围。

输入和结果操作需要兼容中文输入法，组合输入回车不触发打开或提交；键盘导航、焦点恢复、长文件名截断和窄窗口可读性遵循现有[显示基线](../ui-display-readability-baseline.md)。搜索框与结果页不放实现解释性文案。

## 8. 下一步如何选择形式

建议先做少量静态原型或交互草图比较，不直接进入完整功能开发。用同一批示例数据检验：

1. 知道文件名，只想快速打开。
2. 多个目录有同名文件，需要看路径和逐个预览。
3. 不记得名称，靠两个以上标签缩小范围。
4. 搜到 ASMR/漫画作品，同时目录中存在封面、音轨或页面文件。
5. 无结果、部分加载、对象存储不可达，以及窗口变窄、目录树变宽。

需要用户后续选择的是：常驻输入还是图标展开、临时结果还是主区域结果、是否重视边搜边预览，以及普通文件列表与作品封面的优先级。不要在这些决定之前锁死大型分栏、结果卡片或新工作区模式。

实施验证应覆盖名称与后缀、字面特殊字符、目录边界、标签 ANY/ALL、父子标签语义、分页无重复遗漏、过期响应、打开后返回与定位、修改后刷新、多资料库隔离和窄窗口。规模与性能目标需要代表性资料库实测后确定。

文件搜索 UI 尚未实施，本稿不代表其交互或规模性能已经验证。标签基础的验证范围以正式专题为准；后续实测仍禁止使用第一个资料库，优先可用的非首个测试库。
