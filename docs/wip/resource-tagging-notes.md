# 资源标签与 Agent 辅助打标调研

更新时间：2026-10-02

状态：资料库标签基础已实施；Agent 自动打标流程仍为设计草稿。当前契约以[资料库标签](../../../omniflow-go/docs/architecture/library-tags.md)、[标签管理](../tag-management.md)和[Agent 标签工具](../agent-library-tags.md)为准。本文保留未决定的粒度、写入模式和交互空间，不把建议作为实现要求。

适用范围：普通文件、目录、内置类型和归档资源的标签，以及指定目录范围内的 Agent 辅助整理。搜索入口与结果展示另见[文件搜索调研](file-search-notes.md)。

## 1. 目标与目前的决定

用户希望标签能参与未来的文件筛选与搜索，并探索一个独立、类似 Skill 的打标能力：指定某个目录的范围，由内置 Agent 初步打标签，人再调整不合适的结果。

已先落地库内词表、手动定义管理、服务端搜索分页及 ASMR 增量编辑。尚未决定标签继承、自动创建标签、自动写入还是先审核，以及普通资源的完整人工调整入口。

建议把标签用于表达资源的主题、创作者、系列、语言等检索价值，不将它限定在某一种内置类型，也不要求所有文件都必须有标签。标签属于长期整理成果，应遵循[项目长期方针](../../../PROJECT_PRINCIPLES.md)的数据归属、恢复与多设备原则。

## 2. 当前已有的能力

### 2.1 数据与类型边界

| 对象 | 当前作用与限制 |
| --- | --- |
| `tags` | 新资源标签定义属于资料库，按库读写权限访问；未迁移的旧账号/UI 定义保留兼容 |
| `node_tag_rel` | 节点直接绑定标签的权威关系，带资料库归属；包含关系 ID、节点 ID、标签 ID、资料库 ID、创建时间，但没有 AI 来源、置信度或审核状态 |
| `nodes.view_meta.tagIds` | 正式关系的兼容投影；节点配置 PUT 不再用传入的该字段替换关系 |
| `scope / type` | 历史兼容字段；新库标签不按 ASMR、漫画等类型拆词表，`FILE_TAB` 已退出管理界面 |
| `dimension` | 可选自由分类，支持中文；内置作者、语言、题材等仅为建议，默认 `custom` |
| `resourceKind`、`targetKinds`、`tag_bind_policies` | 保留历史结构，新库标签不再受这些资源类型绑定限制 |
| `node_resource_targets` | 数据库维护的节点种类投影；其中的 `source` 是类型投影来源，不是 AI 打标来源 |
| `tag_aliases` | 已有预留结构，尚未接入当前标签搜索/API 闭环 |

文件、目录和作品共用库内标签。资源自身的内置类型与归档模式继续表达结构，不需要为了给图片、音轨或作品打标而增加专用标签目标种类。同库、同分类的规范化名称避免重复；旧定义及迁移映射的保留方式见正式[迁移说明](../../../omniflow-go/docs/architecture/library-tags.md#迁移与恢复)。

**当前没有标签继承。** 给作品目录标记“日语”，不会自动让其中每个音频、封面都命中“日语”标签查询。

### 2.2 操作与界面

- 后端已有读取节点标签和增量修改关系的接口：`GET /api/v1/nodes/:nodeId/tags`、`PATCH /api/v1/nodes/:nodeId/tags`，带资料库上下文；修改支持 `dryRun`。
- 标签定义查询必带 `libraryId`，支持名称字面子串、分类、启用状态与服务端游标分页；页面与 Agent 均不再先下载整个词表。已选标签可按 ID 补齐名称。
- 管理页提供名称、可选分类、颜色、说明、排序和启停；选择器按需查询，切库清理旧结果与草稿。
- ASMR 编辑器从正式关系读取标签，按用户修改的增删差集保存；完整 `viewMeta` 不再覆盖标签关系。停用、删除或遗留标签可回显并移除，遗留定义只读且不可新增绑定。
- 普通文件/目录的通用手动打标体验尚未形成完整闭环。
- 资源关系在服务端，不能因 Agent 会话分组采用客户端存储，就把资源标签也只保存在本机。

## 3. 应该给什么打标签

以下为建议粒度，不是已经落地的自动规则。

| 资源 | 优先打标对象 | 示例与边界 |
| --- | --- | --- |
| 独立文档、笔记、图片 | 该文件节点 | 主题、来源、内容语言；文件名证据不足时读取可用内容或跳过 |
| 独立音频、视频 | 该文件节点 | 创作者、系列、题材；不凭格式推测内容 |
| ASMR、漫画、音乐专辑等完整作品 | 表达作品的根节点，通常是内置类型目录 | 标整部作品，避免封面、歌词、漫画每页得到一份重复标签 |
| 归档或合集 | 合集/归档根节点 | 表达合集主题；不能推断其中每个成员都具备同样属性 |
| 普通目录 | 有检索价值的目录节点 | 项目、专题、来源等组织意义；目录名只是弱证据 |
| 缓存、临时文件、附属素材 | 默认不自动打标 | 由明确任务范围或用户需要再纳入 |

不要仅为搜索而把已有确定性元数据复制成 AI 标签。扩展名、MIME、时长、分辨率、内置类型通常更适合作为结构化筛选；“已读”“喜欢”“重要”等个人状态不能由模型凭内容自行决定。

一个文件是否属于某部作品，应依据已有节点关系与内置类型语义，不靠 Agent 猜测目录名称。混合目录既可能有独立资源，也可能有作品附属资源，不能简单按扩展名批量打标。

### 3.1 父级标签如何影响搜索

例如 `作品 A/` 有“助眠”标签，内部有 `01.wav`、`cover.jpg`：

- 现状：搜索“助眠”直接命中 `作品 A/`，不会自动命中两个子文件。
- 建议的初期行为：保留这一语义，结果可以打开作品；需要时通过既有 viewer 查看成员。
- 可选扩展：提供“包含匹配作品内的文件”或展示来源于父作品的标签，但必须与直接标签区分。

继承不是本轮已确认需求。如果未来需要，优先研究查询或展示时计算来源，避免把同一标签复制到整个子树；还需定义移动、解除绑定和多个祖先标签冲突时的行为。

## 4. Agent 可以复用什么

| 能力 | 当前边界 |
| --- | --- |
| `tag.list` | 查询当前库可用标签或已知节点直接关系；服务端过滤并返回 `cursor` 分页，模型结果有体积限制，不提供全量总数 |
| `tag.update` | 给节点增删已有标签 ID；每个增删列表最多 100 项，不创建/删除标签定义 |
| `library.batch` | 一次最多 50 项，已支持 `tag.update`、`node.configure`、改名、移动、复制；逐项独立提交，不是整体事务 |
| 资料库查询与内容读取 | 可发现目录范围内的候选节点，并按已有工具能力读取内容；不等于具备通用 OCR、语音识别或任意格式理解 |
| Skill 机制 | 提供按需加载的领域知识与流程建议，不裁剪 Run 工具、不授予权限；已有资源整理 Skill，当前没有专用打标 Skill |

因此，不应把“缺少打标工作流”写成“完全缺少批量标签写入工具”。优先复用现有 delta、批处理和运行时权限，不因新增 Skill 再造一套操作边界。

`tag.update` 的 Tool schema 使用 `assess: ask`，实际询问行为还受本次 Run 冻结的组范围与完全访问策略影响，不等于每个文件必定询问一次。现有组访问校验依据节点及祖先关系进行客户端检查，不能视作对服务端并发移动的事务性范围保证。

当前 Run 也没有固定的“最多几轮/几个 Tool Call”上限，不能沿用早期历史稿的数字作为规模设计依据。打标仍需独立的资源、读取、费用和批次数量预算，避免无界扫描。

## 5. 建议的目录打标工作流

### 5.1 先明确任务范围

一次任务应冻结账号、服务端、资料库、根节点、是否递归、是否包含根节点，以及以下策略：

- 打标单位：独立文件、作品根或目录；是否包含附属资源。
- 可用词表及维度：优先复用已有标签，不默认允许模型创造新词。
- 证据范围：仅元数据，还是允许读取指定类型的内容；限制资源数、读取量与调用预算。
- 写入模式：只生成建议，或经用户明确指定后自动增量写入。

任务指定的目录是本次操作范围，即使 Agent 具有更广的完全访问权限，也不应把打标任务扩大到范围外。执行器需要验证目标，而不是只在提示词中写“不要越界”。若要求并发移动时仍严格保证范围，应在后端写入时补充原子校验契约。

### 5.2 发现、判断、提交、核对

1. 分页发现范围内资源，识别作品与附属文件，建立有界待处理清单。
2. 读取当前标签及必要证据；优先复用词表，缺少证据时保留未判定状态。
3. 生成建议和简短依据，区分新增、已存在、无法判断和跳过。
4. 按选定模式审核或提交增量；批量写入可以复用 `library.batch` 的标签动作。
5. 核对实际回执，报告成功、失败、未执行和提交结果不明的范围，支持后续人工调整。

当前元数据查询已返回 `builtInType / archiveMode`，可用于识别作品结构；完整标签详情通过 `tag.list` 按需获取，通用结果仍不包含完整标签、目标种类或封面。领域说明可以给出常见结构、未整理形态和判断线索，不需要把整个 `viewMeta` 暴露给模型。

专用 Skill 若后续加入，应保持克制，以常见粒度、证据和核对方式帮助模型判断；不通过 Skill 裁剪 `library.batch` 子动作或限制其他可用工具。具体动作由用户任务范围和既有运行时权限决定，不要求模型对每种目录照固定步骤执行。

基础打标不需要通用 Shell 或向外部站点上传文件。读取正文时仍遵循现有 Provider、数据访问和内容工具边界；不能把文件内的指令当作任务授权。

### 5.3 写入模式待选

| 方案 | 适用场景 | 需要解决的问题 |
| --- | --- | --- |
| 先建议，用户选择接受 | 词表刚建立、内容不易判断 | 审核成本和建议保存位置 |
| 明确授权后初步自动添加，再人工修正 | 范围和词表明确，符合用户提出的初步打标方向 | 记录新增来源、可核对结果、保护人工修改 |
| 按规则混合 | 已有代表性验证集与稳定分类规则后 | 规则复杂度；模型自报置信度不是经过校准的正确概率 |

本文不替用户选定模式。初期建议只自动添加已有标签，不自动移除人工标签；遇到词表缺口先提出候选，避免出现大量近义词。

## 6. 人工纠正、恢复与多设备

当前关系表不能识别“AI 添加”“人工确认”或“用户拒绝过”。若自动打标只是每次重新猜测再写入，用户删除的不合适标签会在下次运行时回来，这是需要提前解决的缺口。

若后续实施持续自动打标，再按实际使用需要定义以下能力；不把它们都作为基础标签或首版 Skill 的前置条件：

- 建议的来源、依据、任务关联与状态；建议表只是候选方案，没有确定表名或 schema。
- 已接受标签的来源及人工确认状态；只保存建议、不记录接受后的关系变化，不足以实现可靠撤销。
- 用户拒绝/移除建议后，何时允许再次建议，例如内容变化或用户显式重置。
- 撤销仅处理本任务确实新增且尚未被后续操作改变的关系，保留任务前已有和人工确认的标签。
- 对新增、确认、拒绝的并发修改采用明确的冲突检查，不能用旧快照覆盖。

资源标签及应跨设备保留的人工修正属于服务端资料数据。待审核建议、任务进度是否跨设备恢复，需要另定持久化范围；不能将它与本地 Agent 会话组混为一谈。重要标签关系和人工修正也应纳入导出与备份设计。

批处理取消不等于撤销；已提交项继续有效。`commit_unknown` 要先查询核对，不能盲目重放。现有 `library.batch` 的逐项回执可复用，但尚不等于完整的任务恢复与撤销能力。

## 7. 后续决策与验证

下一步先用现有标签基础验证手动整理和检索需求，再以真实案例判断是否需要专用打标 Skill。写入模式、粒度与人工纠正可小步试用，不预先堆叠审核规则。新增后端表结构仍按规范先迁移、再生成 model/query。

待决定：作品与普通文件的默认纳入规则、父级标签展示方式、标签创建权限、人工修正入口、建议与任务记录的持久化范围。

未来验收至少覆盖：

- 普通文件、内置作品、归档与附属资源混合的目录；内容证据不足时合理跳过，跨库或不可用标签不能新增绑定。
- 目录外节点、已移动/删除节点、切换账号或资料库；执行范围与权限不能因批处理失效。
- 超过 50 项时分页分批；部分成功、取消、超时与结果不明都能核对。
- 重复运行不重复添加，也不恢复用户明确拒绝的标签；撤销不损坏人工整理。
- 父作品与子文件查询语义一致；跨设备读取同一份权威标签关系。

基础标签的实施与验证记录以正式专题为准。本稿尚未验证模型自动打标质量、完整任务恢复或撤销；查询具备索引与分页也不代表热门标签、短关键词和任意数据规模已有性能保证。
