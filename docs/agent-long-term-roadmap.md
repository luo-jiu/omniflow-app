# OmniFlow Agent 长期规划

更新时间：2026-09-11

适用范围：`omniflow-app` 内置 Agent 的模型适配、资料库交互、本机执行、工具协议、上下文管理和用户体验。

## 1. 目标

OmniFlow Agent 面向两类任务：对内熟悉地操作 OmniFlow 资料库，对外提供接近 Codex 的本机开发体验。目标不是把所有能力都集中到 Shell，而是让 Agent 根据资源所在位置和任务动作选择正确的执行平面。

目标体验：

```text
OmniFlow 资料库：结构化、可验证、可恢复的文件和内容操作
本机宿主环境：明确授权、可审计、可靠的开发工具执行
Run 工作区：隔离的中间产物、转换和临时工作目录
```

## 2. 核心边界

Agent 始终区分三套命名空间：

| 平面 | 示例 | 主要用途 |
| --- | --- | --- |
| `library` | `/文档/report.pdf` | 资料库目录、节点、标签、回收站、内部文档 |
| `run` | `input/a.txt`、`output/result.pdf` | 暂存、转换、生成和中间产物 |
| `host` | `/Users/me/project`、`~/Desktop/a.txt` | 本机文件、Git、npm、编译器和真实 Shell |

scope 是资源和每次 Tool Call 的属性，不是整个会话的全局开关。一个任务可以跨越多个平面，但跨平面必须通过专用桥接工具完成。

当前路由规则：

- 用户明确给出本机、桌面、下载、`~/`、`/Users/` 或 Windows 盘符时，使用 `host`。
- 用户提到资料库、目录树、标签、回收站或 OmniFlow 内部路径时，使用 `library`。
- 转换、生成和需要工作副本的操作优先使用 `run`。
- 本机文件原样进入资料库使用 `file.upload`。
- 本机或资料库文件需要转换后进入资料库，使用 `file.stage` → `shell.run` → `file.publish`。
- 资料库内部的创建、读取、重命名、移动、复制、删除、恢复和标签操作使用结构化 Tool，不使用 Shell 模拟。

## 3. 当前状态与执行方式

### 已完成

- 资料库目录浏览、搜索、路径定位、属性读取和正文读取。
- 资料库文本文件直接创建和基于 revision 的修改。
- 资料库目录创建、重命名、移动、复制、移入回收站、回收站查询和恢复。
- 标签查询与原子增删，保留未指定的标签关系。
- PDF、DOCX、XLSX、PPTX 附件处理；资料库文档 Tool 已接入同一处理引擎。
- Tool 的 owner、账号、资料库、Session、Run 和提交状态校验。
- `committed`、`uncommitted`、`commit_unknown` 三态结果及失败后的核对提示。
- 目录树、选中项、预览标签和媒体资源的节点变更同步。
- `library`、`run-workspace`、`host` 三种 Shell 执行语义。
- macOS Zsh 的 `ask`、`auto`、`full-access` 权限模式开发预览。
- 多图和文档附件、图片视觉输入、PDF/DOCX/XLSX/PPTX 工具读取。
- OpenCode 风格的历史正文清理和终态历史压缩基础能力。
- 按模型目录解析上下文窗口；已知 OpenAI 模型使用内置窗口，未知模型默认 128K，并保留接口元数据和真实 overflow 校正方向。
- 操作账本基础：复用会话 SQLite 中持久化的 ToolRun 结果，`operation.verify` 先查操作状态再核对资料库资源。

### 当前限制

- 资料库复制和标签接口已完成后端实现、故障注入测试和真实存储联调；标签更新超时后的真实 UI 核对已完成，复制断线场景仍需验收。
- 资料库文档 Tool 已接入受控 `imageId` 结果，仍需继续扩大真实资料库样本的视觉验收。
- 批量移动、批量重命名、批量复制和批量标签更新已形成部分成功协议，并覆盖冲突、取消和 `commit_unknown` 测试。
- 本机结构化编辑仍主要依赖 Shell，尚未有稳定的 `apply_patch` Tool。
- Go 后端生产 bootstrap 已切换为 owner 级 `LibraryAuthorizer`；独立成员角色、service identity scope 和非 library 资源授权仍未收口。
- Linux 和 Windows 的 Agent Shell 仍未完成与 macOS 同等级别的执行验收。
- 回收站恢复后的自动目录刷新、节点上下文清理和统一节点事件仍需持续验证。

### 阶段状态

| 阶段 | 状态 | 当前结论 |
| --- | --- | --- |
| 模型预算与基础稳定性 | 基础完成 | 模型目录、切换重算、恢复发送和压缩已有实现与自动化测试；真实小窗口长任务仍需补一次端到端验收。 |
| 资料库文档专家 | 基础完成 | PDF、DOCX、XLSX、PPTX 的 inspect/read/query/view 和边界测试已具备；真实样本和 UI 展示仍需扩大验收。 |
| 基础文件操作与批量整理 | 基础完成 | 单项、批量、部分成功、冲突、取消和核对能力已具备；同一 OmniFlow 会话中的目录刷新和结果展示已验证，真实断线重试仍需验收。 |
| 本机代码编辑闭环 | 未开始 | 仍缺少 main-owned 的 `apply_patch` 和 revision 冲突闭环。 |
| 权限和可靠性收口 | 进行中 | 重试、结果核对、标签超时和本地操作账本已有基础；owner 级授权已接入，成员 RBAC、service identity 和后端跨进程账本尚未收口。 |
| 跨平台宿主执行 | 未完成 | macOS 有开发预览，Windows / Linux 仍需等价验收。 |

当前应连续推进“权限和可靠性收口”中剩余的真实 UI / 断线验收，完成后再开始 `apply_patch`，不要重新重复已经通过的基础工具开发。

### 连续执行规则

后续工作按完整阶段推进，不按单个文件、单个测试或单个工具拆成独立任务。一个阶段至少应连续完成“实现或修复 → 自动化验证 → 真实联调或替代性验证 → 文档更新 → 工作树检查”这一整个闭环，再统一汇报结果。

只有以下情况才允许暂停：

- 需要用户选择产品行为，且代码无法安全假设。
- 需要用户提供当前环境中不存在的账号、样本或外部服务。
- 同一个外部阻塞连续重试三次仍没有变化。
- 继续执行会覆盖用户或其他 agent 的未提交改动。

测试失败、服务未启动、端口被占用、开发窗口连接错误、需要重启本地服务，都属于执行过程中的问题，应由执行者自行处理后继续推进。局部完成不构成阶段完成，也不应因此结束任务。

## 4. 分阶段路线

每个阶段都按一个连续工作包执行。完成标准全部满足后，才进入下一阶段或汇报阶段性结果。

### 阶段一：模型预算与基础稳定性

目标是让模型切换、恢复发送和上下文压缩不会因为旧预算或错误模型信息直接失败。

工作项：

- 维护 Codex 风格的内置模型目录，覆盖模型窗口、最大窗口、输出预算、推理等级、Tool Calling、图片和并行工具能力。
- 已知模型优先使用可信目录；服务端 `/models` 用于补充能力，不允许错误的小窗口覆盖已知模型身份。
- 未知模型使用 128K 起始估计，并在真实 `context_length_exceeded` 后校正。
- 模型切换后重新计算当前请求，不能沿用上一个模型的预算。
- 恢复失败草稿时先执行发送前历史压缩，再按当前模型重新投影 Tool schema 和附件。
- 固定 Tool schema 超限时优先收窄当前任务无关的工具，不静默丢弃当前用户消息。

连续工作包：补齐模型目录和预算来源，验证切换模型、恢复带附件消息、长任务压缩和真实上下文超限；修复失败后重新运行完整测试，并在同一个 OmniFlow 会话中验证自动继续。

完成标准：所有场景都能给出可解释状态，并能在有空间时自动继续；不能只以单元测试通过作为阶段完成。

### 阶段二：资料库文档专家

目标是让资料库文件和聊天附件使用同一套处理语义。

工作项：

- 资料库文件提供 `inspect/read/query/view` 文档能力。
- PDF 按页读取和渲染，DOCX 读取正文，XLSX 支持工作表、范围、筛选和统计，PPTX 按幻灯片顺序读取文字、备注并在可用时渲染。
- 统一源存储可达性检查、文件大小、版本、取消、超时、分页和结果预算。
- 图片结果只通过受控 artifact/image 引用进入 Provider，不把 Base64 或物理下载地址写入持久化记录。
- 文档解析失败、扫描页、缺失公式缓存、外部资源和不完整结果必须明确区分。

连续工作包：为四类格式补成功、授权失败、不可达、版本变化、路径推导和视觉结果测试，再用真实资料库完成一次“定位文件 → 检查格式 → 读取或查看 → 分析 → 写入结果”。

完成标准：Agent 能在资料库内完成上述闭环，无需用户下载再上传，且失败原因可解释。

### 阶段三：基础文件操作与批量整理

目标是让 Agent 能安全完成日常资料库整理。

工作项：

- 将单项操作和批量操作统一到 ResourceRef/节点快照概念。
- 支持搜索结果批量移动、重命名、复制和标签增删。
- 每项记录 `pending`、`committed`、`uncommitted`、`commit_unknown`、`skipped`、`conflict` 等状态。
- 支持部分成功，返回已完成、冲突、跳过和未知项，不能因为一项失败回滚已经成功的独立项。
- 批量操作前重新读取目标节点和目标目录，锁定 owner、资料库、版本和冲突策略。
- 批量操作后刷新来源目录、目标目录、选中状态、预览 tab 和 Agent 感知。
- 网络中断时提供核对 Tool，优先按 operation identity、目标路径和节点状态对账，再决定是否继续。

连续工作包：补齐批量操作 mock 测试，模拟冲突、取消、网络中断和提交不明；再使用同一个 OmniFlow 会话完成真实批量整理、结果核对和目录刷新。

完成标准：Agent 能完成“搜索 → 选择结果 → 分类移动/改名 → 打标签 → 核对结果”，清楚报告部分成功和需要人工处理的项目，且重试不会制造重复副作用。

### 阶段四：本机代码编辑闭环

目标是把本机开发体验提升到稳定的 Codex 70～80 分水平。

工作项：

- 新增 main-owned 的 `apply_patch` Tool，支持结构化增删改、上下文匹配和多文件 patch。
- patch 必须绑定文件 revision，文件被用户修改后拒绝覆盖并要求重新读取。
- 支持 dry-run、差异预览、审批、取消、失败清理和提交状态核对。
- Shell 继续负责搜索、格式化、编译、测试、Git、npm、Python 和媒体工具命令。
- Shell 输出、Tool result、审计记录和 UI 摘要继续使用不同预算层，不把完整日志塞回模型上下文。
- 统一显示操作平面，例如 `本机 · ~/project`、`Run · output`、`OmniFlow · /文档`。

连续工作包：先完成 `apply_patch` 的协议和冲突测试，再在真实本机项目中执行读取、精确修改、测试、查看 diff 和冲突恢复。

完成标准：Agent 能完成完整编辑闭环，过程不依赖 heredoc 或整文件覆盖。

### 阶段五：权限和可靠性收口

目标是让前端路由正确之外，后端也能独立阻止越权和错误副作用。

工作项：

- 将 Go 后端 `AllowAll` 替换为 actor、library owner、成员权限和资源动作校验。
- 收紧通用文件上传和文件链接接口的认证与资料库绑定。
- Agent Tool 使用独立、可审计的 service identity 和 library scope。
- 所有内部写操作保留事务、审计、dry-run、提交回执和不确定结果对账。
- 复制、迁移和外部资源操作不能复用或泄露源对象凭据。
- 通过 fail-closed 测试覆盖跨账号、跨资料库、跨后端、过期节点和路径漂移。

完成标准：即使模型输出错误 nodeId、path 或 provider，也无法访问或修改不属于当前 owner/library 的资源。

### 阶段六：跨平台宿主执行

目标是补齐本机 Agent 的平台覆盖和退出可靠性。

工作项：

- 完成 macOS Zsh 的真机长任务、取消、重连、孤儿进程和权限模式验收。
- 增加 Windows PowerShell 和 Linux Bash 的等价 Provider 与进程树回收。
- 针对路径、符号链接、reparse point、UNC、大小写、环境变量和临时目录建立平台测试。
- 保持 host 与 run-workspace 的路径语义严格分离。
- 评估 OS sandbox、持久规则和更强执行身份，未满足条件前保持 fail-closed。

完成标准：三平台都能执行受控本机命令，取消和崩溃不会留下未管理进程或临时资源。

## 5. ResourceRef 演进

ResourceRef 是内部统一概念，先作为 Tool 执行前的 main-owned 规范化结果，不立即替换全部公开 Tool 参数。

```ts
type ResourceRef =
  | { scope: 'library'; libraryId: number; nodeId?: number; path?: string; revision?: string }
  | { scope: 'host'; capabilityId: string; displayPath: string; revision?: string }
  | { scope: 'run'; workspaceId: string; logicalPath: string };
```

外部 Tool 参数仍可使用自然路径、节点 ID 或逻辑路径；进入执行阶段后必须解析成带 scope 的内部引用。宿主真实路径、存储 key、签名 URL、凭据和 workspace 物理路径只由 main 持有。

## 6. 评测与验证

建立 20 至 30 条固定路由评测，覆盖：

- “这个文件”在当前目录、资料库路径和本机路径下的歧义。
- 资料库文件不可达但元数据可见。
- 本机文件原样上传和转换后发布。
- 模型切换、恢复发送和上下文压缩。
- 单项和批量写入的冲突、取消、提交不明与重试。
- 文档正文、扫描页、公式缓存、备注和渲染。
- 跨账号、跨资料库、过期 nodeId 和路径漂移。
- 权限询问、完全访问、拒绝后停止和不换工具重试。

自动化测试覆盖协议、权限、预算、失败状态和资源释放；真实桌面验收优先使用非第一个资料库，当前环境优先 win 资料库。真实 MinIO、API 和模型联调结果必须记录 Run ID、模型、资料库和关键 ToolRun，不把模型最终回答单独当作证据。

## 7. 暂不做

- 向量检索和复杂 RAG，直到元数据、正文读取和批量整理稳定。
- 旧版 Office、OCR 和通用二进制格式，除非实际任务频率证明需要。
- 永久删除、自动清空回收站和无确认的不可恢复操作。
- 让 Shell 直接操作资料库数据库、MinIO 或绕过内部 Tool 的权限链路。
- 把所有模型的提示词完整复制到 OmniFlow；只引入与工具路由、权限和工作流直接相关的必要适配信息。

## 8. 维护规则

以下变化必须更新本文档：

- 新增 scope、ResourceRef 或跨平面桥接。
- 新增模型目录字段、模型能力或上下文预算来源。
- 新增内部文件写操作、批量操作、文档格式或 Host Provider。
- 修改权限、提交状态、重试、压缩或结果核对语义。
- 完成一个阶段或改变阶段优先级。
