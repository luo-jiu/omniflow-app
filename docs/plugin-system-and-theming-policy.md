# OmniFlow 插件系统与主题扩展方针

更新时间：2026-09-13

适用范围：OmniFlow 整体插件化方向，包含 `omniflow-app` 桌面宿主、工作区、文件与目录查看器、主题和图标，以及 `omniflow-go` 向插件提供业务能力的边界。

状态：**长期演进方针，尚未实现完整第三方插件平台。** 本文记录发展原则、阶段顺序与合格标准；接口名称和字段示例是设计示意，不是已经发布的 SDK。具体实现仍须遵守各项目 `AGENTS.md` 和现有专题契约。本方针仅涉及插件向内部 Agent 提供 Tool 贡献的接入边界；内部 Agent 的通用功能和全量迁移不在此路线内。

执行入口：[插件化实施计划](plugin-system-implementation-plan.md)，记录第 1～3 阶段的代码调研、实施批次、兼容要求与验收门槛；实际进度以该计划及其验收记录为准。

当前 C1 实验事实与限制见 [SDK 与隔离实验](plugin-system-c1-sdk-isolation.md)：已完成独立构建、自动隔离及 macOS 原生交互验证；[C2 第一方 CSV](plugin-system-c2-csv-viewer.md) 已通过 macOS 实际链路验收，[D1 本地管理与恢复](plugin-system-d1-management.md) 已验证 macOS 受限只读安装，[D2 第二功能与开发包](plugin-system-d2-external-development.md) 也已完成技术验证，本轮 macOS 只读链路收口；不代表完整第三方平台或其他平台已验收。

## 1. 目标与核心原则

目标是让开发者能够独立制作、安装和维护插件，扩展文件处理、内容展示、工具流程和外观，而不必修改 OmniFlow 源码。核心系统提供稳定的数据与桌面能力，插件通过公开接口增加功能，主题通过独立外观协议改变样式。

**成熟后的开发方式：新增业务功能默认优先开发插件，核心持续维护公共能力、权限、事务、兼容与运行稳定性。** 已有 SDK 能完成的功能，目标是能独立开发、打包和更新，无需为了增加该功能修改主壳或重新发布整个客户端。核心仍需要维护；本方针不承诺今后所有需求都只改插件。

前期允许“开发插件，同时补齐平台接口”。新增能力超出当前 SDK 时，先明确所缺的通用接口，随兼容的宿主版本交付，再由插件声明最低版本或能力要求。随着接口稳定，重复修改核心的需求应减少；仅把功能移动到一个名为 plugins 的源码目录不算达到目标。

后续开发遵循以下原则：

1. **渐进扩展。** 从主题、图标、命令和只读查看器开始，用真实插件验证接口，再开放写入、自动处理和服务连接。
2. **公开契约优先。** 插件依赖 SDK、消息协议和语义标识，不依赖宿主内部目录、React Context、DOM 结构或原始 IPC。
3. **状态 owner 单一。** 账号、资料库事务、上传队列、标签页、媒体播放、权限和主题解析继续由核心系统拥有。
4. **权限由执行层落实。** Manifest 声明用途，宿主在每次能力调用时检查真实身份、授权与资源范围。
5. **外观与行为分离。** 配色、图标、目录装饰和目录查看器独立定义；更换外观不改变文件事实或业务语义。
6. **以第一方功能验证 SDK。** 至少一个内置样板功能通过与第三方相同的公开接口完成，不依赖隐藏接口。
7. **兼容、回退和清理属于基础能力。** 插件停用、崩溃、升级失败或缺失时，核心浏览能力和用户数据仍可用。

近期重心为：**主题与图标协议、命令注册表、一个只读查看器 SDK。** 插件商城、服务器插件和任意本机程序执行不作为第一版前置条件。

## 3. 扩展类型与核心保留能力

插件包统一管理安装和版本，一个包可以包含多种贡献；颜色主题和图标包可独立选择，纯外观包不要求执行代码。安装或启用外观贡献不顺带授予同包功能代码读取资料库、访问网络或执行程序的权限。

| 贡献类型 | 典型用途 | 开放顺序 |
| --- | --- | --- |
| 颜色主题 | 背景、文字、交互状态、编辑器配色 | 第一批 |
| 图标与目录装饰 | 文件夹造型、开合图标、文件类型图标、颜色与徽标 | 第一批，优先声明式规则 |
| 文件与目录查看器 | CSV 表格、电子书、模型预览、目录画廊 | 先只读文件，再目录与编辑能力 |
| 命令、菜单与工具页面 | 批量改名、字幕处理、图片压缩、格式转换 | 先注册入口，再开放有副作用能力 |
| Agent Tool | 文件分析、格式检查与结构化查询 | 先单文件只读，复用既有 Run/权限/审计，写能力另行设计 |
| 导入、导出与服务连接 | 网页收藏、外部数据导入、服务同步 | 在文件与网络授权成熟后开放 |
| 存储驱动与服务器任务 | 新存储服务、持续索引、自动处理 | 单独设计管理员权限与部署边界 |

核心保留认证、授权、文件与节点事务、上传提交、存储凭据、标签页和文件树状态、媒体生命周期、主题解析与插件管理。插件通过适配接口使用这些能力，不复制第二套业务事实源。

第一期支持桌面端插件，Go 后端继续提供稳定业务 API。服务器插件以后由管理员安装，明确多用户影响、持续运行与资源限制。当前存储接口带有 S3 预签名和分片上传语义，不能直接承诺所有存储服务都能成为同一种驱动；后续需要单独设计能力差异。

### 3.1 核心、随包官方插件与第三方插件

“是否随应用内置”描述分发方式，“是否属于核心”描述职责，两者分别判断。

| 类别 | 定位 | 例子与约束 |
| --- | --- | --- |
| 核心平台 | 维护基础规则、状态与受控能力 | 插件宿主、授权、文件事务、标签页生命周期、主题解析与最小故障恢复入口 |
| 随包官方插件 | 默认随安装包提供，按插件契约开发与维护 | 官方查看器、字幕工具、主题和图标包可逐步迁移；普通业务插件可停用或替换，停用后核心仍可访问和导出资源 |
| 第三方插件 | 外部作者独立交付 | 使用公开 SDK，按实际能力取得权限；官方来源或随包分发也不能隐式获得越过契约的权限 |

上述例子是迁移方向，不表示现有模块已经插件化。官方插件可与宿主同仓库维护、随宿主发布，不强制独立仓库或首期远程更新；仍需满足独立身份、公开契约和生命周期要求。必要的高权限适配单独留在宿主并提供受控接口，不给官方插件保留可随意调用的内部后门。

### 3.2 新功能归属判断

每次新增功能依次判断：

1. **现有 SDK 能完成目标**：在插件中实现界面、领域算法与流程，不为该插件 ID 在核心新增特殊分支。
2. **缺少可复用的系统能力**：核心补齐最小公开接口及其权限、错误与版本语义，插件承载具体功能；不把整个业务页面或规则搬入核心来代替接口设计。
3. **涉及系统权威规则**：认证授权、事务提交、资源回收和状态 owner 等由核心维护，插件通过请求使用。
4. **涉及暂未开放的高权限能力**：按对应阶段设计独立扩展类别，不能借“插件优先”绕过宿主边界。

例如视频压缩的页面、参数和压缩流程属于插件；来源授权、受控处理程序、取消与文件提交由宿主管理。播放器界面或解码扩展的可行性可以评估，但播放归属、全局控制与关闭释放仍遵守 MediaHub 契约。

插件能力不足时允许继续迭代平台。现有功能按样板逐步迁移，不要求立即拆空核心、重写全部查看器或改变现有目录类型；不以减少核心代码行数衡量成功。决定继续由核心直接实现某项业务功能时，在对应实现说明中写明当前缺口和保留原因。

## 4. 插件契约与运行边界

### 4.1 Manifest、SDK 与宿主

- **Manifest（插件清单）**：声明稳定插件 ID、包版本、SDK 兼容范围、平台与能力要求、按需激活条件、权限请求和扩展贡献。
- **SDK（公开接口）**：提供有类型定义、错误语义和版本约定的能力入口。跨运行环境通过异步消息通信，参数与结果可序列化；大文件通过受控流或句柄传递。
- **插件宿主**：管理包、实例、注册贡献、身份、授权、请求和资源清理；通过适配层调用既有服务与后端用例。

第一版 SDK 聚焦以下能力，名称在实现专题中再冻结：

| 能力组 | 最小职责 |
| --- | --- |
| 上下文 | 当前资料库、受控选中资源、活动视图与变更通知；看到资源引用不等于获得正文权限 |
| 界面与命令 | 打开已注册视图、执行获准命令、显示宿主表单与消息；菜单声明位置、顺序和命令 ID |
| 资源访问 | 分页查询、详情、按需读取；写入阶段增加条件保存、上传、移动与回收站操作 |
| 插件存储 | 自有设置、状态和元数据，按插件与账号及适用资料库隔离，限制容量 |
| 主题与生命周期 | 读取主题快照，订阅切换，声明恢复与关闭行为，登记可释放资源 |

公共 SDK 不直接导出内部 React 组件、store、任意 HTTP 代理、原始 IPC channel、数据库连接或 MinIO 凭据。后端继续复用 usecase 的授权、事务、审计与 dry-run，SDK 适配层吸收内部变化。

### 4.2 隔离与权限

普通第三方代码采用受限 JavaScript／TypeScript 环境，默认不提供 Node.js 文件系统、Shell、主应用 DOM 或用户令牌。简单菜单、按钮和设置表单由宿主按声明渲染；复杂页面使用隔离视图与消息 SDK。权限确认、危险操作确认等关键交互由宿主持有。

具体采用何种 iframe、WebContents 或运行进程组合由样板验证后确定，必须分别验证：

- 样式隔离、脚本权限隔离与故障隔离；Shadow DOM 不能充当安全边界，单独进程也不自动限制文件或网络权限。
- 第三方不能继承主应用 preload、认证 session 或通用 IPC；宿主绑定真实插件实例与消息来源，不相信 payload 自报身份。
- sandbox、contextIsolation、Node 暴露、origin、导航和网络访问配置形成完整边界；不能只在 SDK 名义上限制请求而保留旁路。
- 运行挂死时宿主能停止实例并恢复界面；不能仅依赖插件主动响应取消。

有效权限为：**用户原有权限 ∩ 用户授予插件的权限 ∩ 当前资源范围**。授权可以限定到资料库、节点、用户选择的本机目录和网络目的地，并在调用时复验。主机代管凭据，插件不持有用户完整登录令牌。

升级新增权限需要取得对应授权；撤销后停止新访问，在途操作按取消与提交契约结算。以后如开放任意 Node.js、Python、原生二进制或服务器代码，必须定义独立的高权限扩展类别，不能借普通查看器权限取得执行能力。

## 5. 主题、图标与文件夹样式

### 5.1 语义 token 与统一主题结果

主题按用途提供样式值，例如 `surface.panel`、`text.primary`、`selection.background`、`focus.border`、`status.danger.text`、`folder.archive.label`。这些名称为示意，公开前应冻结 schema 与回退规则。

语义组至少覆盖：

- 表面：应用、侧栏、面板、弹层、输入区。
- 文字与交互：主要／次要／禁用文字、链接、悬停、按下、选中、键盘焦点。
- 状态：成功、警告、危险、信息各自的文字、背景与边框。
- 资源：普通目录、媒体目录、归档与未知类型的视觉语义。
- 辅助：阴影、滚动条、圆角、编辑器背景、光标、选择和语法颜色。

OmniFlow 语义 token 是公开协议；Semi、styled-components 和编辑器主题是内部适配层。沿用现有 ThemeContext 与 `--app-*` 作为演进入口，不为插件化先全量改名或迁移状态 owner；旧主题对象退为适配结果，不能再形成独立权威值。归档外观使用独立语义，不永久借用“成功色”。

覆盖顺序为 **系统默认值 → 主题对应的明暗变体 → 用户覆盖**。插件可提供自己命名空间内的默认 token；主题和用户可按公开规则覆盖。缺失字段回退，非法值拒绝，未知字段报告并按兼容策略处理。

由单一主题 owner 产生带版本的解析快照，主窗口、overlay、编辑器和插件视图订阅同一结果。跟随系统、预览、取消和卸载都需要明确行为；主题不可用时恢复内置默认。隔离视图不能依赖共享 localStorage 来同步主题。

### 5.2 文件夹图标与装饰

处理顺序为 **节点事实 → 目录／文件语义与状态 → 图标主题资产 → 宿主状态装饰**。

- 换颜色、造型、开合图标属于外观；按名称或类型关联图标属于装饰规则。
- 打开目录后呈现画廊、播放器或看板属于查看器功能，独立于主题。
- 更换外观不得修改 `builtInType`、`archiveMode`、文件识别结果、树展开状态或打开行为。
- 图标选择优先级为单节点显式外观、用户关联规则、当前图标包、类型提供者默认值、核心兜底。开合状态缺少资源时有明确回退。
- 宿主树与列表中的错误、离线等必要状态由宿主合成，图标包不能隐去必要提示；不据此承诺第三方自绘界面不可伪造。自定义装饰与共享业务元数据分开存储。

### 5.3 外观包的边界

第一版使用声明式主题数据和校验后的本地图片／SVG，不执行主题脚本。颜色字段不能夹带任意 CSS、远程 `url()` 或全局选择器；资产必须限制包内路径、类型和大小，SVG 处理可执行内容与外部引用。

先开放颜色、图标、阴影和有约束的圆角。字体、密度、间距和行高应在显示基线稳定后按受约束档位开放，变更必须同步列表虚拟滚动、点击热区与布局测量。插件页面 CSS 只作用于自己的视图；主题不通过全局滤镜重着色用户图片、视频或网页内容。

涉及标题栏、透明背景与原生视图时，继续遵守 [桌面平台契约](desktop-platform-architecture.md)、[overlay 契约](overlay-window-architecture.md) 与 [显示基线](ui-display-readability-baseline.md)，不能靠全局缩放或修改窗口能力兜底。

## 6. 数据、生命周期与兼容

### 6.1 数据归属与写入

插件设置、共享文件信息、个人阅读状态和本机缓存分别管理。本机路径与缓存不进入跨设备用户偏好。插件数据以稳定插件 ID 建立命名空间，带 schemaVersion 与 revision；宿主确定可写命名空间，插件只能操作自己的数据。

公开节点元数据写入前，提供命名空间更新和并发版本保护。不得让插件整体覆盖现有 `viewMeta`，也不得直接修改核心标签投影或存储表。卸载默认保留用户文件及插件持久数据，数据清理提供单独选择。

文件写入复用核心业务校验、提交与审计。网络失败、取消或超时不等于没有提交；结果不明确时先核对，不能自动重放写操作。批量任务报告部分成功与失败范围。业务事件在提交后发布；需要可靠后台消费时，再设计持久事件与幂等处理，禁止在数据库事务内执行第三方代码。

### 6.2 生命周期与回退

安装状态与运行实例状态分开。贡献按需激活，实例登记视图、任务、订阅、媒体和资源句柄。宿主统一处理正常关闭、停用、升级、账号／资料库切换、崩溃和应用退出。

正常关闭先通过既有草稿与保存流程解决未保存内容；随后停止准入、取消并结算在途操作、释放资源和移除贡献。紧急撤权或崩溃不等待插件配合，先隔离实例，再由宿主核对已提交动作并恢复可用草稿。不能依赖插件自己的 cleanup 保证回收。

查看器复用既有 tab、会话恢复和媒体 owner；不能另建独立的全局播放器、树状态或上传队列。宿主回收不活跃实例时保护未保存或播放中的状态，并为插件异常提供有界兜底。

### 6.3 版本、包与冲突

- 插件包版本、SDK 版本、数据 schema 版本和事件／任务协议版本分别管理；第一期维护一个 SDK 主版本与能力探测。
- Manifest 校验重复 ID、兼容范围、平台、必要能力和贡献结构；不兼容时明确拒绝激活。
- 安装先校验包完整性与解包边界，再启用；普通插件安装不隐式运行任意安装脚本。来源与发布者可追溯，校验和或签名不等于功能安全证明。
- 更新失败保留可恢复版本；若数据已迁移，必须验证回退兼容或提供数据备份恢复，不能只回退代码包。
- 菜单、命令、查看器 ID 使用插件命名空间。多个查看器匹配时，优先用户本次选择和保存的关联，再按确定规则选择；新安装插件不得无提示接管已有打开方式，不能由安装顺序隐式覆盖。
- 缺少插件时保留资源与必要状态，提供内置查看器、原始文件访问或导出入口；支持禁用第三方扩展后启动以恢复故障。

## 7. 分阶段路线

阶段按验收结果推进，不承诺固定日历工期。样板优先选择一套主题与图标包、一个只读 CSV 查看器、一个批量改名工具，分别验证外观、内容读取与写入。

| 阶段 | 主要交付 | 通过标准 |
| --- | --- | --- |
| 1. 整理入口与外观 | 补齐主题 token、图标映射，抽取命令／菜单／查看器注册入口 | 新增内置贡献无需在主壳到处增加分支；配色与图标独立切换 |
| 2. 验证公开接口 | Manifest、最小 SDK、开发加载与日志；一个第一方样板使用 SDK | 样板独立构建且不导入宿主内部模块；接口有类型、schema 与错误说明 |
| 3. 第三方只读扩展 | 隔离运行、资源读取授权、安装停用、兼容检查与恢复入口 | 外部作者能独立交付查看器；跨插件／账号／资料库越界失败，坏插件可停止 |
| 4. 处理与写入 | 条件保存、上传与批量动作，任务进度、取消、结果核对和网络授权 | 批量改名等样板覆盖冲突、部分成功、撤权、取消和提交结果不明确 |
| 5. 生态与高级扩展 | 发布与更新渠道、可靠自动任务、服务连接；评估存储及服务器扩展 | 由多种真实插件需求推动设计，并分别验证权限、迁移和平台支持 |

第一版不同时引入任意本机代码、通用服务器任务平台、复杂插件依赖图或完整商城。先完成开发加载、手动安装和可用样板，避免为尚未出现的需求维护大规模基础设施。

第 1 阶段的静态注册表只是准备工作。声明“某功能已经插件化”至少需要独立插件身份与包清单、公开接口、贡献加载与实例生命周期、兼容检查、停用与失败回退；只把 switch 改成 registry 不算完成。先贯通一个样板的完整流程，再验证第二个不同功能能否复用契约。

关键需求按以下可观察结果验收：

| 需求 | 必须证明的结果 | 对应阶段 |
| --- | --- | --- |
| 后续主要开发插件 | 在已支持的能力范围内加入第二个不同插件，无需增加主壳分支、插件专用 IPC 或后端专用入口 | 2～4 |
| 内置功能也能采用插件方式 | 官方样板通过公开 SDK 运行；普通业务插件停用后可回退，不遗留资源或损坏用户文件 | 2～3 |
| 他人能够独立开发 | 外部作者使用模板与文档独立构建、安装只读查看器，并在兼容宿主上更新插件包 | 3 |
| 文件夹样式与整体配色可自由组合 | 切换颜色主题和图标包可独立生效，覆盖目录开合和必要状态，文件类型与打开行为不变 | 1～3 |
| 可扩展更多文件处理流程 | 处理插件可读取来源、报告进度、取消与保存结果，失败和部分提交可核对；不绕过权限或核心事务 | 4 |

## 8. 合格标准与验证

各阶段按已开放能力验收；没有实现的能力明确标为不可用，不用占位接口冒充完成。

1. **独立开发**：外部开发者依据文档、SDK 类型和样例完成插件，无需修改或导入宿主源码；提供开发加载／刷新、日志与错误定位。
2. **权限有效**：覆盖拒绝与撤销授权、伪造插件身份、跨账号／库／插件访问、任意 IPC、文件及网络旁路。
3. **故障可恢复**：覆盖异常、死循环、停用、卸载、升级失败和应用重启；主壳可用，不残留资源、播放或失控任务。
4. **数据受保护**：覆盖并发修改、旧状态恢复、迁移失败、缺失插件、部分提交与提交结果不明确；不误删原始文件，不重复写入。
5. **扩展可共存**：验证两个同格式查看器、重复贡献 ID、菜单与快捷键冲突、命名空间数据和样式隔离。
6. **外观完整**：覆盖主窗口、overlay、编辑器与插件视图，亮／暗／系统切换，悬停／按下／选中／焦点／禁用／危险态，以及缺 token、缺图标、主题卸载回退。
7. **性能有证据**：记录启用前后启动、空闲、目录浏览和切 tab 的基线；按需加载、分页／批量通信、快照与输出有界，不逐节点跨进程查询样式。具体预算随样板实测冻结。
8. **平台承诺真实**：按声明的平台完成验证；检查 100% 缩放、Windows DPI、标题栏安全区与原生视图遮挡，未验证平台不宣称支持。

纯文档阶段只检查事实、链接和契约一致性，不代表运行验收。实施阶段执行对应项目要求的 lint、测试、构建和手工验证；使用隔离 fixture，遵守 workspace 禁用第一个资料库、优先使用可达的本机非第一个资料库规则，不默认执行破坏真实数据的测试。

## 9. 待细化决策与维护规则

本方针用于约束需求与方向，不能代替完整实现设计。每个阶段开工时，在对应专题明确以下最小内容，再按第 7、8 节验收推进：

1. 本阶段支持的用户场景、交付物与明确不支持的能力。
2. 最小接口／schema、真实状态 owner、权限和信任边界。
3. 加载、运行、取消、关闭、更新与失败恢复的关键状态流。
4. 对现有用户行为、数据和接口的迁移／兼容影响及回退路径。
5. 成功与失败验收案例，并对应到第 7 节需求和第 8 节合格标准。

实施前按阶段细化：Manifest 与 SDK 的正式 schema、插件宿主隔离方案、授权粒度与撤销语义、主题 token 目录、资源句柄与元数据存储、打包格式及更新策略。本文不预先锁定每插件一个进程、特定 UI 框架、RPC 库或商业分发渠道。

新增扩展点时，应回答：它服务什么真实场景、复用哪个状态 owner、权限如何落实、失败如何清理、旧数据如何兼容、第三方如何验证。优先通过适配层接入现有能力，避免改变现有用户行为与 API / IPC 契约。

如果在已有能力范围内，每个新插件仍要求修改主壳、通用 preload 或核心表结构，官方插件长期依赖私有接口，或插件停用后基础浏览失效，应回到扩展边界重新评估。若出现尚未支持的真实需求，允许补充平台能力，但需说明公共价值与兼容影响，不能为追求“完全不改核心”拒绝合理演进。

改变方针时同步更新本文；能力落地后更新第 2 节事实，并链接相应实现专题与验收记录。阶段流水账放专项文档，本文件长期保留原则、当前边界和未完成项。涉及后端接口、数据库或 CLI 时，另按 `omniflow-go/AGENTS.md` 补齐迁移、生成代码、接口与 CLI 文档，不由本方针替代项目规范。
