# OmniFlow App 文档规范

更新时间：2026-04-15

适用范围：`omniflow-app` 的前端架构文档、模块 README、Electron/IPC 契约说明、交互说明、进度台账和 review 标准。

目标：让文档成为前端开发者和 Coding Agent 的外部长期记忆。文档要回答“当前事实是什么、边界在哪里、改动后怎么验证”，而不是堆积一次性过程记录。

## 1. 基本原则

- **开发前（Read）**：先读 `AGENTS.md`、review 标准和相关专题文档。
- **开发后（Write）**：判断文档是否已经失真；如果失真，就立即修正。

如果判断不需要更新文档，最终回复中要简短说明原因。

## 2. 目录约定

- `.agent-docs/`：前端长期规范、review 标准、交接说明。
- `docs/`：专题说明、专项审计、跨模块设计记录。
- `src/modules/**/README.md`：复杂模块的局部说明，例如上传中心。
- `README.md`：项目介绍、构建方式、能力概览，不承担前端治理规则。

新增文档文件名使用小写英文短横线，例如 `embedded-browser-resource-capture.md`。

## 3. 何时必须更新文档

出现以下任一情况，必须补充或更新对应文档：

- 新增或修改页面入口、路由、工作区模式或核心用户路径。
- 新增或修改 API 请求字段、响应读取方式、错误提示语义。
- 新增或修改 IPC channel、preload 暴露 API、Electron 主进程能力。
- 新增或修改状态 owner、状态机、缓存、持久化 key 或恢复行为。
- 新增或修改嵌入式浏览器、资源捕捉、下载、合并、打开文件能力。
- 新增或修改上传中心、任务生命周期、进度、取消、重试、失败处理。
- 新增或修改主题、布局、安全区、浮层、右键菜单、拖拽交互。
- 新增或修改构建、验证、发布、环境变量或运行方式。
- 修复因业务理解偏差导致的问题，需要澄清文档事实。

## 4. 写作要求

- 全部使用中文撰写，专业术语可保留英文。
- 优先写“当前事实、边界、契约、验证”，少写一次性过程。
- 表格只保留决策有用的信息，避免大面积重复“已完成”。
- 不把大段代码直接贴入文档，用关键规则和流程描述代替。
- 不用截图替代可搜索文本。
- 涉及 token、账号、内网地址、本地绝对隐私路径等敏感信息必须使用 `***` 脱敏。
- 不做无关台账 churn，只更新与本次变更直接相关的文档。

## 5. 推荐结构

新增长期文档优先包含这些部分，按实际需要删减：

```markdown
# 文档标题

更新时间：YYYY-MM-DD
适用范围：说明约束哪些页面、模块或流程。

## 1. 概述
## 2. 核心概念
## 3. 契约
## 4. 实现边界
## 5. 验证方式
## 6. 维护规则
```

阶段性文档完成后，改成“当前结论 + 保留规则 + 未完成或待验证 + 维护规则”的归档摘要，不长期保留大段流水账。

## 6. Agent 自检

Agent 完成一轮前端修改和验证后，必须自检：

1. 本次变更是否影响已有文档的准确性？
2. 本次变更是否引入了后续开发者、设计、前端、后端或 Agent 必须知道的新知识？
3. 本次变更是否涉及 API、IPC、Electron、状态、资源捕捉、上传、主题布局或验证门禁？
4. 如果需要更新文档，是否已同步修改对应文档？
5. 如果不需要更新文档，最终回复是否说明了原因？

## 7. 禁止事项

- 禁止让已完成的进度文档长期保留大段逐项流水账。
- 禁止在文档中记录与代码事实不符的过期描述。
- 禁止把敏感配置、真实 token、密码、内部地址写入文档。
- 禁止用“后续再补文档”绕过 API、IPC、Electron 边界或核心交互变更的文档更新。
