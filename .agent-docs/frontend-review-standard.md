# OmniFlow App Frontend Review Standard

更新时间：2026-10-16

适用范围：`omniflow-app` 前端、Electron renderer / preload / main、IPC、工作区交互和前端文档相关改动的代码评审。

目标：用一份短文统一前端 review 的判断顺序、风险重点、验证门禁和输出格式，避免“功能能跑，但边界和生命周期慢慢变形”。

详细架构、专题边界和验证矩阵请分别参考：

- `AGENTS.md`
- `docs/frontend-architecture-baseline.md`
- `docs/embedded-browser-architecture.md`
- `docs/library-detail-workspace.md`
- `docs/file-explorer-file-viewer-boundary.md`
- `docs/frontend-validation-matrix.md`

## 1. Review 顺序

每次 review 按下面顺序判断，前一层不过，后一层不算过：

1. 黑盒行为和用户心智是否稳定
2. 分层与职责边界是否干净
3. 状态 owner 是否单一、可推导
4. 生命周期与热路径性能是否可靠
5. 主题、布局、浮层和桌面宿主细节是否一致
6. 验证与文档是否收口

## 2. 重点风险面

### 2.1 黑盒行为回归

优先关注：

- 路由、页面入口、工作区模式切换是否漂移
- API / IPC 字段、错误提示、恢复行为是否变化
- 双击、右键、拖拽、返回、关闭 tab 等核心交互是否变化

默认高风险：

- 用户操作路径没变，但结果或反馈变了
- 只改局部功能，却影响别的模式、tab、库或页面
- 原本来自后端或主进程的错误，被前端表现成“像代码坏了”
- 自动恢复/重试期间若输入框仍可编辑，必须验证这段时间新增的草稿不会被旧快照清空或覆盖；不能仅验证恢复后的消息列表。
- 失败发送恢复必须保持正文与附件的关联；用户期间开始编写下一条消息时，不能把旧附件静默拼到新正文下。
- 文档提取/渲染必须区分真实空白与超限、解码失败导致的内容缺失；第三方解析器的警告不能被包装成“完整读取成功”。

### 2.2 分层与边界

默认依赖方向：

```text
views -> features -> components / hooks -> service / bridge -> backend or electron
```

优先关注：

- 页面或通用组件里是否散落原始 IPC / Electron 调用
- `service` 是否开始拼页面状态机
- `features` 是否偷偷承担页面总控
- `electron` 是否反向承担 renderer 业务编排
- 外部文件后缀、类型或方法名用于索引权限白名单时，必须只匹配自有键或使用 Map；不得让 `constructor`、`__proto__` 等继承属性通过能力筛选。
- embedded browser 页面属于未受信任内容；页面 console、DOM 全局变量或可伪造事件不能直接授权 main 执行下载、写盘、凭据读取等重操作，必须经过 isolated world、不可预测 nonce、可信事件和一次性 capability 校验
- Tool 的私有输入投影不能依赖执行可见性：模型或环境过滤、不可用及 unknown-tool 拒绝路径仍按可信注册身份保护原名和 Provider 名称的私有正文，不得写入 SQLite、IPC 或续轮历史；隐私识别不能恢复被过滤的执行能力。
- 新增宿主输入动作必须逐层纳入可信注册、权限准备和 broker 的受监督提交结算，不能只在 runtime 测试里手传结算对象而漏掉真实 Agent 接线。取消期间保留有界的释放回执等待，已结束的未知结算不得被迟到成功覆盖，也不得自动重放。
- 定向输入不能将 PID 投递当作单窗消费证明。持续手势每步复验冻结窗口可见性、接收窗口 / 控件及新出现的临时表面；取消只能向仍有效的原窗口发送唯一配对释放，不能把 up 路由到同 PID 的另一窗口。释放未确认时须实际阻断当前 Run 的后续手势，不能只写拒绝文案；新观察、重批、换窗及已封存动作均不得绕过，结束后的迟到回执不复活门禁。私有坐标 API 缺失须首发前拒绝，软件 / 系统 profile 与真实业务验收证据分别记录。
- 持久合成焦点须只有一个输入会话 owner，跨 Run 交接先等前 owner 清理并真实退出；输入队列串行不代表动作间保留的状态互斥。焦点通知是独立副作用，鼠标零事件不等于完全未提交；鼠标配对释放、焦点清理和原生进程退出分别结算。关闭 ACK、kill 请求及单独 exit 不能冒充焦点清理；清理未知须跨新观察和新 Run 阻断，迟到成功不洗白。事件过滤依赖持续服务的独立 RunLoop，回调不做阻塞 AX 读取；暂停 WindowServer 更新必须在取消和错误路径恢复。合成操作后目标意外成为真实前台，不能仅凭该采样认定用户已接管；有证据的用户接管与尚未完成的旧前台恢复分开持有，无法确认恢复不能报告 released。
- 以事件来源 PID 区分自身与外来输入的持久保护器，须与后续定向键盘和鼠标共享发送进程；不得用任意 helper PID 白名单补齐身份差异。兼容 one-shot 路线派发前先确认旧 owner 清理并退出，失败不得越过 mutation begin；共用 sender 不扩大首条键盘操作的激活权限。
- 快捷键不能成为私有正文审计的按键旁路。若公开 action 和历史保留按键，字母或数字键至少要求 Command 或 Control；裸键、仅 Shift 或 Option 的可打印输入应走已有私有正文文本工具，并验证 schema、shared 归一化和原生边界一致。
- 原生 helper / IPC 的内容限额须包含完整序列化结构、路径与元数据开销；正文和条数均合法时仍可能超过总输出预算。允许部分结果的观察须在生产者侧有界截断并明确完整度，不能让接收端硬上限丢弃全部可用结果。
- 对齐 Codex Computer Use 的改动，应先核对相应服务端函数、状态和调用链，再确定 OmniFlow 设计；已有证据优先复用，未知部分做有界补充分析。记录二进制身份、观察 / 推断 / 未知及实现差异，不能只凭客户端接口名、静态符号或自研假设宣称等效。菜单 AX 根、应用身份、截图集合和光标视觉归属分开验证；菜单是应用上下文时，不强行套用普通窗口 descendants 约束，也不能顺带扩大其他普通窗口或全屏采集。

### 2.3 状态双源

优先关注：

- 派生状态是否被重复存储
- 同一业务事实是否同时存在于页面、feature、ref、宿主投影等多处
- tab、workspace、browser view、tree expansion、selection、draft input 是否各有唯一 owner

默认高风险：

- prop 看似受控，实际只在 mount 时生效一次
- 本地数组镜像主进程或后端状态，靠补丁式 `setState` 维持
- 草稿或临时状态泄漏到另一个实例
- 为了“看起来快”缓存了一份状态，但没有清晰失效条件

### 2.4 生命周期与热路径

优先关注：

- 高频事件里是否有明显 O(n) DOM 工作
- `useEffect` / `useLayoutEffect` 是否被无关 rerender 反复触发
- timer、event listener、upload task、browser tab、WebContentsView、session 是否回收
- Electron main 持有的真实临时文件是否同时具备单文件/总量配额、TTL、导航或 tab 清理、正常退出清理和崩溃残留回收
- 异步回调是否会把旧页面 / 旧 tab / 旧库结果写回当前界面
- 临时 Electron / GUI 测试启动器必须将 Node launcher 与 Electron main 入口明确分开：用显式参数及 `process.versions.electron` 验证运行态，Electron 内只通过内建 `require('electron')` 获取 API，不能用绝对 npm 包路径的返回类型判断运行态。启动前须有进程代数上限、单实例/并发上限、父进程消失清理和独立总时限；先以不启动 GUI 的测试确认最多 spawn 一次、错误入口直接失败，再做实机。`node --check` 不能证明启动生命周期安全；诊断脚本也不得绕过这些门禁。
- 等待用户回答的 Tool 必须有独立等待期限和收口预算，且 host 回调使用执行监督器提供的 Tool signal；不能捕获外层 Run signal 而漏掉工具超时取消。验证须覆盖超过普通工具时限、回答续轮、停止、创建期间取消与真实过期后的 pending 清理；交互终态已落库但回执迟到时，停止或超时不得覆盖真实结算，规范 Tool 仍须有 result 和 finishedAt，不能只检查 Run 状态。

默认高风险：

- 每次 rerender 都全量扫描目录树、tab 或 DOM
- 布局动画需同时核对真实长内容的首帧耗时和阶段提交：祖先上逐帧变化的继承变量会使保留子树样式失效，不稳定回调也会使memo失效。单纯时序正确或空夹具流畅不能替代真实页面的React与布局分项测量。
- 原生 view 已隐藏，但资源和事件还活着
- 用“收起再展开”掩盖同步问题，却影响拖拽或命中体验
- 父组件 layout effect 测量树 / 虚拟列表时，子组件可能尚未完成内部展开或异步渲染；拖拽命中不能依赖这类过期坐标缓存。悬停和 drop 必须核对当前实际覆盖行及视口范围，避免高亮正确性与提交目标分离，也不得用逐帧全量 DOM 测量补偿。

### 2.5 主题、布局与桌面细节

优先关注：

- 亮色 / 暗色 / 跟随系统是否都成立
- 新页面和迁移组件是否复用[通用主题基础](../docs/theme-foundation.md)的表面、文字、选择及交互规则；已有共享入口能表达的状态，不再各页自写颜色。归档/状态语义须能与选中和键盘焦点叠加，不能用选中规则覆盖全部后代文字；样式配置不能替代原生disabled、ARIA或业务状态owner。
- 迁移共享样式须核对实际消费者和CSS优先级：禁用不残留hover/active反馈，Semi显式variant保留前景/底色配对，片段的`font: inherit`不覆盖旧控件字号/字重/行高。主题变量变更运行`npm run theme:audit`，固定色候选结合[覆盖地图](../docs/theme-adoption-map.md)区分内容/品牌/状态，不按数量机械替换。
- 主题颜色动效是否由同一文档的统一边界驱动；不得在 `body *` 对继承的 `color` 添加通配 transition，或让组件对逐帧变化的主题变量再启动过渡。验证须覆盖深层文字与背景的同帧变化、快速反向切换和结束清理，不能只比较动画前后截图；跨窗口与隔离页面的同步范围须明确。
- Canvas等一次性取色消费者是否直接使用只读目标快照或有明确终态更新；只观察class/style并读取动画中的computed CSS可能停在旧/中间色。不能以每帧DOM扫描补偿，也不能另建主题状态源。
- 标题栏安全区、浮层、右键菜单、分栏拖拽是否稳定
- 复用交互控件时核对焦点生命周期：指针操作借用的隐藏输入焦点应在完成或取消后释放，键盘进入则保留；程序触发的 blur 不得重复提交或把取消变成提交，并检查快捷键和依赖 `focus-within` 的自动隐藏。
- 浏览器模式、文件模式、搜索主页切换时布局节奏是否突变
- overlay / modal / context menu 是否会被原生 view 遮挡
- 外部窗口意图图案与真实输入必须保持独立授权和回执。原生窗口no-key/main、穿透、不激活，稳定视觉关联与精确输入观察分离；普通计划完整小窗在当前目标内，计划移动、真实drag / 按压及App active均按目标当前layer相对排序，其他App或同App另一窗自然遮挡，不因移动升102或用orderOut模拟遮挡。只有当前精确绑定且有效的菜单表面授overlay102，允许固定图案外伸但热点须在菜单；菜单计数、数字102或elevated flag不能自行授权。路线证明区域有界、实际小窗仅绘制当前插值点；真实拖拽只显示实际posted反馈，不预播终点。菜单观察必须成对注册/释放，焦点变化不能自动切换授权目标。已知自有窗旧/新几何与层级组合仅在旧表面仍包含且层序安全时可保留像素并有界等待精确终态；菜单撤销后的旧102像素不能作为普通可信可见过渡，否则先清空backing再隐藏/重定位。snapshot须核对普通layer等于已同步目标、菜单为102；淡出仍每帧应用最新菜单状态并复验遮挡，未知状态立即隐藏；视觉跟随不延长旧输入观察，同身份同步只在精确ACK后更新main投影，暂隐保活不等于可捕获；跨Run pending清理与未知关闭全局门禁不能被shown、kill请求或迟到exit替代。
- 光标曲线须验证控制点凸包加完整绘制surface、分段连续端点及统一时间进度，换段复验不能跳帧跨过未经验证区域；长距离不得因单段包围区域上限直接瞬移。首现/移动外层期限须覆盖注册、淡入、全部段间复验和终态收小，不能只统计纯动画时长。正常淡出与取消/失效立即清理区分，淡出中取消可升级；执行身份同步撤销，Run收尾保留原abort监听并等真实关闭，旧清理不能删除新share。同点保持应避免无意义orderOut；自动化外须用真实帧验证弧线及淡出，不以静态首尾图代替。
- 输入旁路反馈只用于光标动画，必须非阻塞、有界、与最终stdout结算隔离；损坏/丢帧/取消不能阻止唯一配对释放。输入settled只清视觉按压，不制造up回执；回调在结算、换share/lease或取消后失效。视觉ready/update/snapshot/closed均不能授权输入或认定应用消费。
- 原生光标截图只接受main持有租约返回的自有小窗身份，复验PID/启动时间/父进程/窗口ID/层级/精确bounds，截图surface须收敛小尺寸；普通窗捕获须在获准原窗内，菜单捕获须与真实获准原窗或已证菜单相交，有限扩边只加入自有图案，不以菜单union中的空白处授权；物理鼠标、音频和额外child windows关闭，不以整屏捕获回退。普通窗口同屏单帧必须精确两窗白名单、唯一显示器完整包含及目标相对sourceRect，关闭menu bar；捕获后目标/光标/显示器变化直接丢图，不能被fallback吞掉。只明确采集失败/超时且原身份仍有效、总预算足够才允许兼容路线；原子成功不得补采底图。跨屏/屏外独立合成的副光标失败保留已采目标，编码失败只复用保留底图；不得重复目标截图或扩张窗口范围。只返回一张canonical PNG，严格核对cursorIncluded与私有captureMethod，统一进入模型/会话/缩略图/大图；新native-window观察禁止renderer再画箭头，缩略图和放大图须验证同图等比例。历史计划SVG兼容仍须精确关联规范动作/前置观察、固定路径、有界PNG/颜色/解码尺寸、deadline/abort/作用域清理，不接受任意SVG/URL。单帧遮挡/非主屏坐标、兼容两窗非原子、动态层级、菜单、真实无干扰与放大边缘均需新实机证据，纯绘图/投递单测不能代替。主题继续只读原owner缓存，不能新增颜色执行IPC或承诺静止即时更新。
- 业务二次确认是否统一走 `openCompactConfirm`，避免 Semi 默认尺寸重新引入旧页面缩放时期的大弹框
- 分栏内浮层必须按实际工作区与祖先裁切边界验证，不能只使用 viewport 宽度；覆盖允许的最大侧栏宽度，并确认浮层最右侧操作仍可见、可点击。

### 2.6 验证缺口

优先关注：

- 是否执行了 `npm run lint`
- 是否执行了 `npm test`
- 是否执行了 `npm run build`
- 是否按 `docs/frontend-validation-matrix.md` 覆盖本次改动对应的主路径和边界路径
- 是否同步更新了真正受影响的文档

## 3. 最低验证门禁

前端 review 的最低门禁：

1. `npm run lint`
2. `npm test`
3. `npm run build`
4. 对本次改动涉及的关键交互做一次人工验证
5. 涉及工作区、文件树、文件预览、上传、embedded browser、资源捕捉、主题或浮层时，至少验证一条边界路径
6. 更新真正受影响的文档或明确说明为什么不用更新

如果没有执行这些验证，不代表不能 review；但必须把未验证风险明确写出来。

## 4. Review 输出格式

Review 结论按这个顺序写：

1. Findings，按严重度排序
2. Open questions / assumptions
3. Change summary

Findings 优先关注：

- 行为回归
- 边界不清
- 状态双源
- 生命周期泄漏
- 热路径性能问题
- 主题 / 布局 / 浮层一致性问题
- 验证缺口

如果没有问题，要明确写“未发现问题”，并补一句残余风险或未验证项。

## 5. 一票否决项

出现以下任一情况，默认不建议合并：

- 破坏用户黑盒行为且未明确说明
- 同一业务事实出现双 source of truth 且无收口计划
- 把原始 IPC / Electron 实现细节散到页面、组件或通用 hook 层
- 在拖拽、滚动、选择、resize 等热路径里引入明显 O(n) DOM 工作
- 用全局主题、窗口配置或禁用安全能力去掩盖局部问题
- 原生资源、事件监听、定时器、异步任务没有明确回收

## 6. 维护规则

这份文档只保留 review 判断标准，不承担架构导览或专题说明。

出现以下情况时，先更新本文，再继续正式 review：

- 最近连续出现、本文还没覆盖的同类 finding
- 前端主要风险面发生变化
- 构建、验证或 review 输出方式发生真实变化
