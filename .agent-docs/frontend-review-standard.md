# OmniFlow App Frontend Review Standard

更新时间：2026-04-12

适用范围：`omniflow-app` 前端代码评审与改造评估。  
目标：用一份短文统一前端的契约、分层、状态、交互性能、Electron 边界与文档门禁，降低“功能能跑，但结构慢慢变形”的风险。

当前基线（review 前先核对，漂移就更新本文）：
- React 18 + TypeScript 5 + Vite 5
- Electron 30
- `@douyinfe/semi-ui` + `styled-components`
- 目录语义以 `views / features / components / service / electron / utils` 为主

如果以下任一条件成立，本文件默认需要先更新再继续 review：
- React / Electron / Vite / Router / UI 组件库出现大版本升级
- 新增了明显的架构层或入口层，例如新的全局状态层、桥接层、工作区容器层
- 出现连续两次以上、本文尚未覆盖的同类 review finding
- 构建、校验、截图验证、测试策略发生了真实变化

## 1. Review 目标顺序

每次 review 按这个顺序判断，前一层不过，后一层不算过：

1. 黑盒行为和用户心智是否稳定
2. 分层与职责边界是否干净
3. 状态所有权是否单一、可推导
4. 热路径性能与生命周期是否可靠
5. 主题、布局与交互细节是否一致
6. 校验、验证与文档是否收口

## 2. 黑盒稳定性

前端改动默认要保持以下契约稳定，除非需求明确要求变更：

- 路由、hash、query、页面入口语义
- API / IPC 请求字段名、响应读取方式、错误提示语义
- 本地持久化状态 key 与恢复行为
- 双击、右键、拖拽、快捷键、返回/进入这类核心交互语义
- 浏览器模式、文件模式、搜索主页这类工作区切换规则

出现以下情况，优先判为高风险：

- 用户操作路径没变，但结果或视觉反馈明显变了
- 只改了局部功能，却影响了别的模式/标签/库的状态
- 错误实际上来自后端或原生层，但前端把它表现成“像代码坏了”

## 3. 分层与职责边界

当前前端默认按下面的责任方向审查：

`views -> features -> components / hooks -> service / bridge -> backend or electron`

Review 时重点检查：

- `views`
  - 负责页面级编排、模式切换、路由落点
  - 不承载细碎业务规则和底层通信细节
- `features`
  - 负责单个业务域的状态编排和交互逻辑
  - 不把跨页面总控逻辑偷偷塞回 feature 内
- `components/ui`
  - 保持通用、可复用，不知道具体业务语义
- `service`
  - 收敛 HTTP / IPC / 上传 / 认证头 / 错误映射
  - 不拼页面交互，不直接操纵视图状态
- `electron`
  - 收敛原生窗口、浏览器视图、下载、会话等宿主能力
  - 不反向承担 renderer 里的业务编排
- `utils`
  - 保持纯函数或轻量工具，不偷偷持有跨模块状态

默认视为分层泄漏的情况：

- 页面或通用组件里散落原始 IPC channel 名称
- UI 组件直接知道后端响应外壳细节
- `service` 里开始拼接页面状态机
- 为了修一个局部交互，把全局主题、窗口或 Electron 安全配置一起改掉

## 4. 结构与拆分标准

优先小步、最小必要改造，不为“看起来整齐”而拆。

建议标准：

- 单文件超过 `500` 行，且已经混合了 2 类以上职责，再考虑拆分
- 单个 feature 同时出现“页面编排 + 数据请求 + 原生桥接 + 重度样式逻辑”时，需要收口
- 拆分优先沿业务边界、状态边界、宿主边界进行
- 不要为了复用几行 JSX 就新增一层抽象

新增抽象只有在以下情况才合理：

- 消除重复业务规则
- 收紧状态所有权
- 隔离 Electron / 浏览器宿主能力
- 把热路径逻辑从视图渲染里移出去

## 5. 状态所有权标准

每份状态必须能回答“谁拥有、谁写入、谁只是消费”。

Review 时重点检查：

- 派生状态是否可以由现有 source of truth 直接算出，而不是再存一份
- 同一份业务事实是否同时存在于 `view state / feature state / ref / native state` 多处
- tab、workspace、browser view、tree expansion、selection、draft input 是否各有唯一 owner
- 离开页面、切换库、关闭标签、释放资源时，状态与原生资源是否同步收尾

常见高风险问题：

- prop 名字看起来受控，实际只在 mount 时生效一次
- 本地数组镜像了主进程或后端状态，后续靠补丁式 `setState` 维持
- 一个空白页/临时页的 draft 泄漏到另一个实例
- 为了“看起来快”，缓存了一份状态，但没有明确失效条件

## 6. 热路径性能与生命周期

前端 review 不只看“功能对”，还要看“交互密集时会不会抖”。

重点检查：

- `dragover`、`mousemove`、`scroll`、`resize`、`selection sync` 这类热路径是否有 O(n) DOM 读写
- `getBoundingClientRect`、强制布局、classList 批量操作是否落在高频事件里
- `useLayoutEffect` / `useEffect` 是否被无关 rerender 反复触发
- timer、event listener、upload task、browser tab、WebContentsView、session 是否有清理
- 异步回调是否会把旧 tab / 旧页面 / 旧库的结果写回当前界面

默认高风险：

- 每次 rerender 都全量扫描目录树或标签栏 DOM
- 外部拖拽 session 没有稳定结束点
- 原生 view 已隐藏，但资源和事件还活着
- 通过“收起再展开”掩盖数据同步问题，却影响拖拽和命中体验

## 7. 主题、布局与交互一致性

OmniFlow 是桌面应用，不是普通网页，review 时必须额外检查宿主环境细节：

- 亮色 / 暗色 / 跟随系统三种主题是否都成立
- 标题栏拖拽区、mac 红绿灯安全区、浮层定位、分栏拖拽缝隙是否稳定
- 浏览器模式、归档模式、文件模式切换时头部高度和视觉节奏是否突变
- 滚动条、hover、selected、active、disabled 在不同模式下是否一致
- 临时调出来的 overlay / context menu / confirm 是否会被主内容或原生 view 遮挡

不推荐的做法：

- 用一次性硬编码位移去“调到差不多”
- 只在当前机器看着对，就把尺寸常量写死
- 为了修单一模式，破坏别的主题或布局节奏

如果必须写偏移量，应至少满足：

- 有明确命名
- 能说明依赖的头部/工具栏高度
- review 时要顺手检查是否还能从布局结构推导掉

## 8. API / IPC / Electron 边界

前端和后端、主进程之间的边界要尽量窄、稳定、可替换。

Review 时重点检查：

- HTTP 请求是否仍通过统一请求层收敛鉴权、错误处理、响应拆包
- IPC 能力是否通过集中桥接暴露，而不是在页面里到处 `window.electronAPI.*`
- renderer 和 main 之间的事件 payload 是否明确、稳定、最小必要
- 下载、浏览器标签、上传、文件打开这类原生能力是否有明确 owner 和释放时机

高风险信号：

- 同一能力同时存在两条不一致的入口
- renderer 为了方便直接依赖 main process 内部状态结构
- debug 日志、诊断快照长期混在正式运行路径

## 9. 校验与验证门禁

前端 review 的最低门禁：

1. `npm run lint`
2. `npm run build`
3. 对本次改动涉及的关键交互做一次人工验证
4. 若涉及主题、拖拽、浮层、浏览器视图、目录树，至少验证一条失败或边界路径
5. 更新真正受影响的文档或本文件

当前仓库没有完整前端自动化测试门禁时，不代表可以跳过验证；  
要把“具体手测了什么”写清楚，而不是只写“已测试”。

## 10. Review 输出格式

Review 结论按这个顺序写：

1. Findings，按严重度排序
2. Open questions / assumptions
3. Change summary

Findings 优先关注：

- 行为回归
- 边界不清
- 状态双源
- 生命周期泄漏
- 热路径性能问题
- 主题 / 布局 / 浮层一致性问题
- 验证缺口

如果没有问题，要明确写“未发现问题”，并补一句残余风险或未验证项。

## 11. 一票否决项

出现以下任一情况，默认不建议合并：

- 破坏用户黑盒行为且未明确说明
- 同一业务事实出现双 source of truth 且无收口计划
- 把原始 IPC / Electron 实现细节散到页面与组件层
- 在拖拽、滚动、选择等热路径里引入明显 O(n) DOM 工作
- 用全局主题、全局窗口配置或禁用安全能力去掩盖局部问题
- 原生资源、事件监听、定时器、异步任务没有明确回收

## 12. 时效性维护规则

这份文档不是一次性定稿，而是 review 基线。

每次准备引用它做正式 review 时，先用 30 秒检查下面 4 件事：

1. 这里写的技术栈版本和主要目录语义还对不对
2. 最近两周的 review finding 里，有没有反复出现但文档没覆盖的问题
3. 这份文档是否还反映当前最容易出事故的区域
4. 是否存在“文档要求已经落后于实际开发方式”的地方

如果答案里有一项是否定的，就先更新：

- `更新时间`
- 当前基线
- 对应章节的规则或一票否决项

目标不是把文档越写越长，而是让它持续代表“现在这套前端真正需要守住的边界”。
